and the process for joining or stepping down from the maintainer team.

Maintainers agree to uphold the [Code of Conduct](CODE_OF_CONDUCT.md) and follow
the project's [contribution guidelines](CONTRIBUTING.md).

## Roles and Responsibilities

- **Code review:** Review pull requests constructively, explain decisions and
  verify appropriate tests and documentation before merging.
- **Issue triage:** Investigate bugs, clarify requests and help contributors agree
  on a focused scope before implementation.
- **Architecture and compatibility:** Preserve canonical Markdown, read-only
  query behavior and explicit review before canonical mutations. Discuss core
  Graph/Wiki identity, schema and compatibility changes before implementing them,
  as described in the contribution guidelines.
- **Release management:** Coordinate versions, changelogs, CI qualification,
  package checks and publication. Credit contributors in release notes.
- **Community support:** Help users and contributors, keep documentation useful
  and uphold the Code of Conduct.
- **Availability:** Communicate changes in availability and arrange a handoff for
  responsibilities that need continued attention.

Maintainer status documents responsibilities. Repository access, branch
protection and package-publishing permissions are managed separately.

## How to Become a Maintainer

Maintainer nominations consider:

1. **Sustained contributions:** Useful code, documentation, reviews or issue
   triage that demonstrate ongoing involvement.
2. **Technical judgment:** Understanding the relevant parts of MEX and its
   compatibility, correctness and testing expectations.
3. **Constructive collaboration:** Clear communication and adherence to the Code
   of Conduct.
4. **Willingness to maintain:** Agreement to take responsibility for an area and
   support other contributors over time.

There is no fixed minimum tenure or pull-request count. Contributions and
readiness are considered together.

## Nomination Process

An existing maintainer may nominate a contributor through a GitHub issue or pull
request, describing their contributions and proposed responsibilities. The
candidate must agree to the nomination.

Current active maintainers discuss the nomination and reach agreement before
adding the candidate through a pull request to this file. Any required repository
or publishing access is reviewed separately.

## Stepping Down

A maintainer may step down or narrow their responsibilities through a pull
request to this file. When stepping down, they can move to the Emeritus list
with their contribution areas and an agreed handoff.

After six consecutive months of inactivity without notice, active maintainers
should contact the person before proposing a move to Emeritus. Any change is
discussed and recorded through a pull request; it does not remove credit for
past contributions.
