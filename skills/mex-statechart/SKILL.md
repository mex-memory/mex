# MEX statechart

Make behavior easier for a human to understand. Generate only on user intent. If a diagram would obscure the explanation, use a better explanation. A prior agent answer identifies the subject; verify it independently against current code.

1. Identify the bounded subject, reader, and implemented/proposed/agreed-model scope. Read current source and useful tests. Query `mex wiki query "<subject>" --limit 5 --json` before broad knowledge discovery; inspect matched terms and grounding health, then read live records. Fall back to Router-directed Markdown if unavailable. Use bounded `mex timeline --query "subject" --file known/path --limit 10 --json` only when history might matter. Verify historical applicability. Fresh Graph may locate evidence; call edges are not state transitions. Never refresh indexes on a read.
2. Retain context only when it changes or explains a state, event, condition, rule, exception, recovery, or abstraction. Record the precise connection and provenance. Keep source/requirement conflicts visible. Omit irrelevant context; do not manufacture a MEX contribution.
3. Read [the baseline modeling workflow](references/upstream-workflow.md) and [runtime instructions](references/toolchain.md). Preserve TLA+ and real TLC checks in normal generation. Reuse agreed rules with provenance; seek agreement only for new inferred rules or material conflicts. Never weaken a rule to get a passing result.
4. Work outside the repository in scratch space. Use the bounded `scripts/runtime.mjs workflow` entry, not the unbounded original scripts directly. Preserve existing TLA+ reference specifications and their authored configurations unchanged. Both from-spec and agreed-chart directions, settled-state rules, narrower observation points, projected overviews, independent regions, goals, proposed fixes and reference comparisons remain available.
5. Assemble and validate the v1 artifact described in [artifact contract](references/artifact.md). Retain models, configs, mapping, rules, raw temporal traces, omissions, toolchain and regeneration. Use stable identities, not captions. Run `check` on the artifact to record actual TLC results. For finite traces, map every numbered state/action back to the same graph and retain raw counterexamples. Goals are expected reachability witnesses, never product bugs. Use runtime summary counts, not counts inferred from the drawing. Missing mappings leave alignment unverified.
6. Attempt each modeled implementation bug through real observable code entry points. Separate what execution reproduced, what source inspection supports, and what was not reproduced. Revisit the model when reproduction disagrees. A passing model proves only the configured model and bounds; unavailable/cancelled/resource-limited checking is never success.
7. Deliver the artifact's fenced Mermaid first in supporting chat. Run `terminal` for the deterministic text fallback when native rendering is unestablished or incomplete. Keep domain labels readable; details belong beside the overview. Disclose every material omission. Write the artifact’s own Mermaid to a scratch `.mmd`, run `workflow render` on that file, and inspect the resulting image and numbered paths as generation QA; images are optional exports, not mandatory viewing. State diagram validity, checker outcome, implementation reproduction, and evidence freshness separately.
8. Optionally `register` the validated artifact into the repository's ignored temporary preview store. Report its route and expiry; this is checkout-only and nothing is shared. Do not launch Hub or fabricate localhost links. On explicit request, use normal `mex hub` authentication/launch and the returned route. Hub Save reviews the exact retained content and creates a new immutable snapshot; commit/push remains separate. Regeneration creates a new preview and never updates old evidence baselines.
